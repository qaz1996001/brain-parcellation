## 2. 安全分級概述（Classification Overview）

### 2.1 分級原則

IEC 62304 基於**軟體故障可能造成的傷害嚴重度**將軟體分為三級：

| 安全級別 | 定義 | 傷害後果 | 關鍵詞 |
|---------|------|---------|--------|
| **Class A** | 軟體系統不可能造成傷害 | 無傷害 | Impossible to cause injury |
| **Class B** | 軟體系統可能造成非嚴重傷害 | 輕微傷害 | Non-serious injury possible |
| **Class C** | 軟體系統可能造成死亡或嚴重傷害 | 死亡或嚴重傷害 | Death or serious injury possible |

### 2.2 評估依據

安全分級**不是**基於：
- ❌ 醫療設備的類型（診斷、治療、監測）
- ❌ 設備的 FDA 分類（Class I/II/III）
- ❌ 軟體的複雜度或規模

安全分級**是**基於：
- ✅ 軟體故障可能造成的**最嚴重傷害**
- ✅ 風險分析的結果（與 ISO 14971 配合）
- ✅ 軟體功能在整體系統中的作用

## 3. 分級詳細定義與範例（Classification Details）

### 3.1 Class A — 不可能造成傷害

#### 定義
軟體系統的故障或失效**在任何情況下都不可能**對患者、使用者或他人造成傷害。

#### 關鍵特徵
- 軟體不影響診斷或治療決策
- 軟體不控制任何可能造成傷害的功能
- 即使軟體完全失效，也不會造成安全風險

#### 典型範例

**✅ Class A 範例 1：醫院資訊系統（HIS）數據備份模組**
- **功能**：定期備份患者記錄到備份伺服器
- **故障影響**：備份失效 → 數據丟失風險增加，但**不直接**造成傷害
- **分級理由**：備份失敗不會立即影響臨床決策或治療，主系統仍可正常運作

**✅ Class A 範例 2：電子病歷（EMR）報表生成工具**
- **功能**：生成患者就診統計報表（用於行政管理）
- **故障影響**：報表錯誤 → 統計數據不準確，但不影響臨床治療
- **分級理由**：報表僅用於管理目的，不影響患者護理

**✅ Class A 範例 3：醫療設備操作培訓模擬器**
- **功能**：提供虛擬環境讓醫護人員練習設備操作
- **故障影響**：模擬器故障 → 培訓中斷，但不影響真實患者
- **分級理由**：僅用於培訓，不涉及真實臨床場景

### 3.2 Class B — 可能造成非嚴重傷害

#### 定義
軟體系統的故障或失效可能造成**非嚴重傷害**，但**不會**造成死亡或嚴重傷害。

#### 關鍵特徵
- 軟體影響診斷或治療，但有其他安全措施
- 軟體故障可被及時發現並糾正
- 傷害是可逆的、短期的

#### 嚴重性判斷（非嚴重 vs 嚴重）

**非嚴重傷害（Class B）**：
- 可逆的臨時傷害
- 不需要專業醫療干預即可恢復
- 輕微的不適或疼痛

**嚴重傷害（Class C）**：
- 不可逆或長期傷害
- 需要醫療干預
- 嚴重殘疾或器官功能損害
- 生命威脅

#### 典型範例

**✅ Class B 範例 1：非侵入式血壓監測軟體**
- **功能**：讀取袖帶血壓計數據並顯示
- **故障影響**：錯誤血壓讀數 → 可能導致不當用藥調整 → 輕微不適
- **分級理由**：
  - 有多次測量機會（重複測量可發現異常）
  - 醫護人員會綜合其他指標判斷
  - 短期內不會造成嚴重後果
- **安全措施**：異常值警報、多次測量比對、臨床驗證

**✅ Class B 範例 2：康復訓練遊戲軟體（物理治療輔助）**
- **功能**：根據患者動作給予即時反饋，輔助復健
- **故障影響**：錯誤的運動建議 → 肌肉疲勞或輕微扭傷
- **分級理由**：
  - 患者在物理治療師監督下使用
  - 傷害僅限於肌肉疲勞或輕微扭傷（可恢復）
  - 不涉及生命支持或重症治療

**✅ Class B 範例 3：糖尿病飲食管理 App（建議型）**
- **功能**：根據血糖數據提供飲食建議（不自動給藥）
- **故障影響**：錯誤的飲食建議 → 血糖輕微波動 → 短期不適
- **分級理由**：
  - 患者自行決定是否採納建議
  - 有頻繁的血糖監測可發現異常
  - 不直接控制胰島素給藥

### 3.3 Class C — 可能造成死亡或嚴重傷害

#### 定義
軟體系統的故障或失效可能造成**死亡或嚴重傷害**。

#### 關鍵特徵
- 軟體直接影響生命維持或關鍵治療
- 軟體故障可能導致不可逆的傷害
- 沒有足夠的外部安全措施來緩解風險

#### 典型範例

**✅ Class C 範例 1：胰島素泵控制軟體**
- **功能**：根據血糖讀數自動計算並注射胰島素
- **故障影響**：
  - 過量注射 → 低血糖休克 → 可能昏迷或死亡
  - 注射不足 → 高血糖酮症酸中毒 → 可能器官損傷或死亡
- **分級理由**：
  - 軟體直接控制藥物給藥
  - 故障後果立即且嚴重
  - 患者可能在睡眠中無法察覺異常
- **安全措施**：雙重劑量驗證、異常檢測、緊急停止機制

**✅ Class C 範例 2：呼吸機控制軟體**
- **功能**：控制呼吸頻率、潮氣量、氧氣濃度
- **故障影響**：
  - 呼吸參數錯誤 → 低氧血症或高碳酸血症 → 腦損傷或死亡
  - 呼吸機停止 → 窒息 → 死亡
- **分級理由**：
  - 軟體直接維持生命功能
  - 重症患者無法自主呼吸
  - 故障後果幾分鐘內即可致命

**✅ Class C 範例 3：放射治療劑量計算軟體**
- **功能**：計算腫瘤放射治療的輻射劑量分佈
- **故障影響**：
  - 劑量過高 → 嚴重組織損傷 → 器官壞死或死亡
  - 劑量過低 → 治療失敗 → 腫瘤惡化 → 生命威脅
- **分級理由**：
  - 劑量計算錯誤直接影響治療結果
  - 輻射損傷不可逆
  - 沒有立即的反饋機制可發現錯誤

**✅ Class C 範例 4：心臟起搏器控制軟體**
- **功能**：監測心律並在需要時提供電刺激
- **故障影響**：
  - 未能提供必要的起搏 → 心臟驟停 → 死亡
  - 不當的起搏頻率 → 心律失常 → 可能致命
- **分級理由**：
  - 軟體直接控制心臟功能
  - 患者依賴設備維持生命
  - 故障後果立即且致命

**✅ Class C 範例 5：手術機器人導航軟體**
- **功能**：引導外科醫生進行精密手術（如腦部手術）
- **故障影響**：
  - 定位錯誤 → 誤傷關鍵血管或神經 → 永久性殘疾或死亡
  - 運動控制失誤 → 嚴重組織損傷
- **分級理由**：
  - 軟體直接影響手術精度
  - 手術區域涉及生命關鍵組織
  - 傷害不可逆

## 4. 安全分級評估流程（Classification Process）

### 4.1 評估步驟

```
步驟 1：識別軟體系統
    ↓
步驟 2：進行危害分析（ISO 14971）
    ↓
步驟 3：評估最嚴重的可能後果
    ↓
步驟 4：考慮風險控制措施
    ↓
步驟 5：確定安全分級
    ↓
步驟 6：文檔化分級理由
    ↓
步驟 7：審查與批准
```

### 4.2 決策樹（Decision Tree）

```
軟體故障是否可能造成傷害？
├─ 否 → Class A
└─ 是 → 繼續評估
    │
    傷害是否可能是嚴重的或致命的？
    ├─ 否 → Class B
    └─ 是 → Class C
```

### 4.3 評估考量因素

#### 傷害嚴重性判斷

| 考量因素 | Class A | Class B | Class C |
|---------|---------|---------|---------|
| **直接性** | 無直接影響 | 間接影響臨床決策 | 直接影響生命功能 |
| **時間性** | 不適用 | 有時間發現與糾正 | 立即或短時間內發生 |
| **可逆性** | 不適用 | 可逆、短期影響 | 不可逆或長期影響 |
| **替代措施** | 不適用 | 有替代方案或監測 | 無有效替代措施 |
| **患者依賴性** | 不依賴 | 部分依賴 | 完全依賴 |

#### 風險控制措施的影響

風險控制措施（如冗餘設計、警報系統）**可以**降低風險的嚴重性，但**不能**僅因為有控制措施就降低分級。

**原則**：
- ✅ 考慮控制措施**失效後**的最壞情況
- ✅ 假設單點故障可能發生
- ❌ 不能假設外部系統（如醫護人員監督）總是有效

**範例**：
- 血壓監測軟體（有醫護監督） → 仍可能是 Class B（如果錯誤讀數可能導致錯誤用藥）
- 胰島素泵（有低血糖警報） → 仍是 Class C（因為警報也可能失效）

## 6. 常見問題（FAQ）

### Q1: 軟體只是數據展示，為什麼不是 Class A？

**A**: 如果展示的數據**影響臨床決策**（如血壓、血糖、心率等），即使只是「展示」，錯誤的數據也可能導致錯誤的診斷或治療。因此可能是 Class B 或 Class C。

**判斷關鍵**：
- 數據是否用於診斷或治療決策？
- 錯誤數據是否可能導致傷害？
- 是否有其他機制可以發現錯誤？

### Q2: 軟體有醫護人員監督，可以降低分級嗎？

**A**: **不能**僅因為有人類監督就降低分級。必須假設人類也可能犯錯或無法及時發現異常。

**原則**：
- 考慮最壞情況（如夜間、人員疲勞、緊急情況）
- 不能假設外部因素（人類監督）總是有效

### Q3: 軟體有自檢功能和警報系統，可以降低分級嗎？

**A**: 風險控制措施（如警報）**可以降低風險等級**，但在確定安全分級時，仍需考慮**控制措施失效**的情況。

**範例**：
- 胰島素泵有低血糖警報 → 仍是 Class C（因為警報也可能失效或患者無法回應）

### Q4: 同一設備中不同軟體模組的分級可以不同嗎？

**A**: **可以**。應該對每個軟體模組（或軟體項目）分別進行安全分級。

**範例**：
- 患者監護儀：
  - 生命體徵監測模組 → Class C
  - 用戶介面模組 → Class B
  - 數據存儲模組 → Class A

### Q5: 分級可以在開發過程中改變嗎？

**A**: **可以**。當以下情況發生時，應重新評估分級：
- 軟體功能發生重大變更
- 識別到新的危害
- 風險控制措施改變
- 使用環境或用戶改變

**流程**：
1. 重新進行危害分析
2. 更新分級評估
3. 調整文檔與測試要求
4. 重新審查與批准

### Q6: 所有醫療設備軟體都需要分級嗎？

**A**: **是的**。IEC 62304 要求所有醫療設備軟體都必須進行安全分級，並根據分級實施相應的生命週期活動。

## 9. 附錄：分級案例研究（Case Studies）

### 案例 1：遠程心電圖監測系統

**系統描述**：
- 可穿戴式心電圖設備
- 即時傳輸心電數據到雲端
- AI 分析心律異常並發送警報給醫護人員

**安全分級評估**：

| 軟體模組 | 功能 | 分級 | 理由 |
|---------|------|------|------|
| **數據採集模組** | 讀取心電信號 | Class C | 錯誤的信號可能導致漏診嚴重心律失常 |
| **AI 分析引擎** | 檢測心律異常 | Class C | 漏報心肌梗塞可能致命 |
| **警報系統** | 發送緊急通知 | Class C | 警報失敗可能延誤搶救 |
| **用戶介面（患者端）** | 顯示心率趨勢 | Class B | 顯示錯誤可能引起恐慌但不直接致命 |
| **數據存儲模組** | 備份歷史數據 | Class A | 數據丟失不會造成立即傷害 |

### 案例 2：糖尿病管理 App

**系統描述**：
- 患者手動輸入血糖數據
- 提供飲食與運動建議
- **不自動控制胰島素給藥**

**安全分級評估**：

| 軟體模組 | 功能 | 分級 | 理由 |
|---------|------|------|------|
| **飲食建議引擎** | 根據血糖提供飲食建議 | Class B | 錯誤建議可能導致血糖波動（輕微） |
| **運動建議引擎** | 建議運動強度 | Class B | 不當建議可能導致低血糖（可糾正） |
| **數據可視化** | 顯示血糖趨勢圖 | Class A | 顯示錯誤不直接影響治療（患者仍需自行判斷） |
| **提醒功能** | 提醒測血糖或服藥 | Class A | 提醒失敗不直接造成傷害（患者有其他提醒方式） |

**關鍵因素**：
- 患者自行決策（不自動給藥）→ 降低風險
- 有頻繁的血糖監測反饋 → 可及時發現異常
- 因此為 Class B 而非 Class C
