## 1. 測試計畫概述（Test Plan Overview）

### 1.1 測試目的

本測試計畫涵蓋 IEC 62304 要求的三個測試層級：
- **單元驗證**（Unit Verification）— IEC 62304:5.5
- **整合測試**（Integration Testing）— IEC 62304:5.6
- **系統測試**（System Testing）— IEC 62304:5.7

### 1.2 測試範圍

**包含**：
- 所有軟體需求（SR）的驗證
- SOUP 整合測試（IEC 62304:5.6.5）
- 風險基測試（ISO 14971 整合）
- 非功能性測試（效能、安全、可用性）

**不包含**：
- 硬體測試（由硬體團隊負責）
- 使用者驗收測試（UAT，由客戶執行）
- 上市後監控（Post-Market Surveillance）

### 1.3 測試策略

**基於風險的測試**（Risk-Based Testing, IEC 62304:5.7.2）：
- 高風險功能（Class C） → 100% 測試覆蓋
- 中風險功能（Class B） → 85% 測試覆蓋
- 低風險功能（Class A） → 70% 測試覆蓋

**測試金字塔**：
```
        ┌──────────────┐
        │ 系統測試 (10%)  │  ← 端到端場景
        ├──────────────┤
        │ 整合測試 (30%)  │  ← 模組間互動
        ├──────────────┤
        │ 單元測試 (60%)  │  ← 函數/類別級
        └──────────────┘
```

## 2. 單元驗證計畫（Unit Verification Plan）

> 本節對應 IEC 62304:5.5 — 軟體單元實施與驗證

### 2.1 單元測試準則（IEC 62304:5.5.2）

**驗收準則**：
- 每個軟體單元 **SHALL** 有對應的單元測試
- 單元測試 **SHALL** 涵蓋正常路徑與異常路徑
- 關鍵單元（Class C）**SHALL** 達到 100% 分支覆蓋率
- 所有單元測試 **SHALL** 自動化執行

**測試設計原則**：
- 獨立性：單元測試不依賴外部系統（使用 Mock/Stub）
- 可重複性：測試結果一致且可重現
- 快速性：單元測試套件 < 5 分鐘執行完畢

### 2.2 單元測試案例範例

#### TC-UNIT-001: 患者數據驗證（PatientDataValidator）

**測試單元**：`PatientDataValidator.validate()`
**追溯 SR**：SR-DATA-001
**測試類型**：單元測試（正常流程）

**測試步驟**：
1. **GIVEN** 有效的患者數據對象
   ```python
   patient_data = PatientData(
       patient_id="P-00001234",
       name="John Doe",
       date_of_birth=date(1980, 1, 1),
       gender=Gender.MALE,
       blood_type=BloodType.A_POSITIVE
   )
   ```
2. **WHEN** 調用 `validator.validate(patient_data)`
3. **THEN** 返回 `True`（驗證通過）

**預期結果**：驗證通過，無異常拋出

---

#### TC-UNIT-002: 患者 ID 格式驗證（異常流程）

**測試單元**：`PatientDataValidator.validate()`
**追溯 SR**：SR-DATA-001
**測試類型**：單元測試（異常處理）

**測試步驟**：
1. **GIVEN** 無效的患者 ID（格式錯誤）
   ```python
   patient_data = PatientData(
       patient_id="INVALID-ID",  # 錯誤格式
       ...
   )
   ```
2. **WHEN** 調用 `validator.validate(patient_data)`
3. **THEN** 返回 `False` OR 拋出 `ValidationError`

**預期結果**：驗證失敗，明確錯誤訊息

## 3. 整合測試計畫（Integration Testing Plan）

> 本節對應 IEC 62304:5.6 — 軟體整合與整合測試

### 3.1 整合測試策略

**整合順序**（Bottom-Up Integration）：
```
階段 1: 數據層 + 業務邏輯層
    ↓
階段 2: 業務邏輯層 + API 層
    ↓
階段 3: API 層 + UI 層
    ↓
階段 4: 完整系統整合
```

### 3.2 整合測試案例範例

#### TC-INT-001: 患者數據端到端流程

**測試範圍**：UI → API → Service → Database
**追溯 SR**：SR-FUNC-001, SR-DATA-001
**測試類型**：整合測試（端到端）

**測試前置條件**：
- 測試數據庫已初始化
- API 服務已啟動
- UI 測試環境可用

**測試步驟**：
1. **GIVEN** 使用者已登入系統
2. **WHEN** 從 UI 建立新患者（填寫表單 → 提交）
3. **THEN**
   - API 返回 201 Created
   - 數據庫中存在新患者記錄
   - UI 顯示成功訊息並跳轉到患者詳情頁

**驗證點**：
- [ ] API 回應正確（狀態碼、資料格式）
- [ ] 數據庫記錄正確（欄位完整、時間戳記）
- [ ] UI 狀態更新正確

---

#### TC-INT-002: SOUP 整合測試（PostgreSQL）

**測試範圍**：應用 → Database Wrapper → PostgreSQL (SOUP)
**追溯條款**：IEC 62304:5.6.5 (測試 SOUP 整合)
**測試類型**：SOUP 整合測試

**測試目的**：驗證 SOUP 隔離層正確處理異常

**測試場景**：
1. **Scenario 1: 數據庫連線失敗**
   - **GIVEN** PostgreSQL 服務停止
   - **WHEN** 嘗試執行查詢
   - **THEN** 拋出 `DatabaseConnectionError`（非 SOUP 原生異常）

2. **Scenario 2: 數據完整性違反**
   - **GIVEN** 嘗試插入重複的主鍵
   - **WHEN** 執行 INSERT 操作
   - **THEN** 拋出 `DataIntegrityError` 且事務回滾

**驗證點**：
- [ ] SOUP 異常被正確轉換為應用層異常
- [ ] 錯誤訊息清晰且可操作
- [ ] 系統狀態保持一致（無資料損壞）

### 4.3 系統測試案例範例

#### TC-SYS-001: 生命體徵監測完整流程（關鍵場景）

**測試範圍**：完整系統（感測器 → 軟體 → 顯示 → 警報）
**追溯**：SR-FUNC-010, SR-ALARM-001, HS-001 (風險控制)
**測試類型**：系統測試（功能 + 風險基）
**安全級別**：Class C

**測試前置條件**：
- 生命體徵監測硬體已連接
- 系統已完成自檢
- 測試患者數據已建立

**測試步驟**：
1. **GIVEN** 系統正常運作，患者已連接感測器
2. **WHEN** 感測器開始監測生命體徵（心率、血壓、血氧）
3. **THEN**
   - 生命體徵數據即時顯示在 UI（< 1 秒延遲）
   - 數據數值在正常範圍內（60-100 bpm, 90-140/60-90 mmHg, ≥95% SpO2）
   - 歷史數據正確儲存

4. **WHEN** 模擬異常生命體徵（心率 > 100 bpm）
5. **THEN**
   - 系統觸發黃色中優先級警報（IEC 60601-1-8）
   - 警報訊息顯示「心率過快：120 bpm」
   - 警報聲音正確發出（間歇蜂鳴）
   - 警報事件記錄到日誌

6. **WHEN** 模擬感測器數據錯誤（心率 = -999）
7. **THEN**
   - 系統檢測到異常數據
   - 系統觸發紅色高優先級警報「感測器數據異常」
   - 系統**不顯示**錯誤數據（防止誤導）
   - 系統記錄錯誤事件

**驗收標準**：
- [ ] 所有步驟都按預期執行
- [ ] 警報回應時間 < 2 秒
- [ ] 異常數據被正確識別並處理
- [ ] 無假陰性（遺漏警報）
- [ ] 無假陽性（誤報警報）

### 4.4 效能測試計畫

**測試目標**（SR-PERF-xxx）：

| 指標 | 目標值 | 測試方法 | 工具 |
|------|--------|---------|------|
| 生命體徵顯示更新 | < 1 秒 | 實時性測試 | 手動計時 |
| API 回應時間 | < 500 ms | 負載測試 | JMeter, k6 |
| 並發使用者數 | ≥ 100 人 | 壓力測試 | Locust |
| 數據庫查詢 | < 200 ms | 效能分析 | pgBench |

**負載測試場景**：
- 50 使用者同時登入
- 100 併發 API 請求（患者數據查詢）
- 持續 30 分鐘穩定運行
